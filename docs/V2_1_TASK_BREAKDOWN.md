# AI 简历筛选工作台 V2.1 开发任务拆解

## 1. 文档定位

本文档用于将 `V2_TASK_BREAKDOWN.md` 中“第三批：V2 可选增强”的关键能力，以及真实试用中暴露出的跨岗位上传入口缺口，拆解为 V2.1 可开发、可验收的工程任务清单。

- [HR_RESUME_SCREENING_TOOL_DESIGN.md](./HR_RESUME_SCREENING_TOOL_DESIGN.md)
- [HR_RESUME_SCREENING_TOOL_V2_DESIGN.md](./HR_RESUME_SCREENING_TOOL_V2_DESIGN.md)
- [V2_TASK_BREAKDOWN.md](./V2_TASK_BREAKDOWN.md)
- [V2_ACCEPTANCE_GUIDE.md](./V2_ACCEPTANCE_GUIDE.md)

说明：

- V2.1 不是重复定义 V2 已完成能力，而是承接 V2 第三批可选增强中的重复候选人识别、岗位标准版本和推荐报告导出，并补充统一上传入口。
- V2 已完成的工作台、上传队列、候选人筛选、AI 解释、备注时间线、轻量人才库和岗位管理增强不在本文档中重复拆解。
- ZIP 批量上传、文本粘贴录入和岗位标准变更后的批量重新评分仍保留为后续增强，不进入 V2.1 第一批范围。
- 若 V2.1 实施中改变 V2 主流程、模块边界或合规边界，需要同步更新上位设计和 V2 任务拆解文档。

## 2. 阶段目标

V2.1 的目标是在当前 V2 已完成工作台、上传队列、候选人筛选、AI 解释、备注时间线、轻量人才库和岗位管理增强的基础上，继续补齐真实试用中的关键缺口。

V2.1 重点解决：

- 简历上传入口从“岗位内上传”升级为“统一上传 + 明确岗位归属”。
- 候选人数据从“每次上传创建新候选人”升级为“可识别疑似重复，避免数据沉淀混乱”。
- 岗位 JD 和筛选标准变更开始具备版本追溯能力。
- 候选人详情中的 AI 判断可以转化为可沟通的推荐材料。

V2.1 不改变当前岗位驱动主流程，也不引入完整 CRM、复杂权限体系或候选人自动合并。

## 3. 核心原则

- 保留现有岗位内上传入口，不破坏当前 V2 主流程。
- 新增统一上传入口，上传时必须选择归属岗位。
- 第一版重复识别只提示，不自动合并。
- 候选人状态、评分、备注、时间线仍必须绑定真实岗位归属。
- 人才库仍是轻量候选人沉淀，不扩展为完整 CRM。
- 岗位标准版本用于追溯评分依据，不替代 HR 人工判断。
- 推荐报告导出只做辅助沟通材料，不作为自动录用或淘汰依据。

## 4. V2.1 核心流程

### 4.1 统一上传流程

```text
进入统一上传页
  -> 选择归属岗位
  -> 批量上传简历
  -> 每份简历生成上传任务
  -> 解析简历
  -> 执行疑似重复候选人识别
  -> 无重复：创建新候选人
  -> 有疑似重复：创建新候选人并展示重复提示
  -> 基于归属岗位生成匹配评分
  -> 在上传队列和候选人详情中展示归属岗位与重复提示
```

### 4.2 岗位内上传流程

```text
进入岗位详情
  -> 上传简历
  -> 自动使用当前岗位作为归属岗位
  -> 复用统一上传处理链路
```

## 5. Phase 18：统一上传入口与重复候选人识别

### 5.1 目标

提供一个跨岗位的统一简历上传入口，上传时显式选择归属岗位，同时在解析后识别疑似重复候选人，降低候选人数据重复沉淀风险。

### 5.2 后端任务

#### 5.2.1 新增统一上传 API

新增接口：

```text
POST /api/resumes/upload
```

请求参数：

```text
job_id: string
file: UploadFile
```

第一版保持单文件接口，前端批量上传时逐个调用，复用现有处理链路。

保留现有岗位上传接口：

```text
POST /api/jobs/{job_id}/resumes/upload
```

岗位内上传接口继续可用，内部应复用统一上传处理服务。

#### 5.2.2 抽取上传处理服务

将当前上传、保存文件、创建上传任务、解析、生成候选人、评分、生成解释、写入时间线等逻辑从 API 层抽取为服务函数。

目标：

- 统一上传入口和岗位内上传入口共用同一套处理逻辑。
- 避免两个上传入口出现行为分叉。
- 后续 ZIP 上传、文本粘贴录入可继续复用。

#### 5.2.3 明确归属岗位标签

第一版继续复用现有字段：

```text
ResumeFile.job_id = 上传归属岗位
UploadProcessingTask.job_id = 上传任务归属岗位
CandidateJobStatus = 候选人在岗位下的状态
```

说明：

- 上传时必须写入 `job_id`。
- 统一上传页选择的岗位即为 `ResumeFile.job_id`。
- 岗位内上传页自动使用 URL 中的 `job_id`。

#### 5.2.4 新增疑似重复识别服务

解析生成候选人后执行重复识别。

建议识别规则优先级：

```text
1. 手机号完全匹配
2. 邮箱完全匹配
3. 姓名 + 手机后四位
4. 姓名 + 邮箱前缀
5. 姓名 + 城市 + 当前岗位/公司相似
```

第一版建议实现：

```text
手机号完全匹配
邮箱完全匹配
姓名 + 城市
```

说明：

- 重复识别只做提示，不自动合并。
- 不覆盖已有候选人。
- 不自动复用已有候选人参与新岗位评分。

#### 5.2.5 新增重复检查记录模型

建议新增轻量表：

```text
candidate_duplicate_checks
```

字段建议：

```text
id
candidate_id
job_id
resume_file_id
matched_candidate_id
match_reason
confidence
status
created_at
```

`status` 可选值：

```text
pending_review
ignored
confirmed_duplicate
```

第一版只生成 `pending_review`，不实现合并。

#### 5.2.6 Schema 与接口返回

上传结果建议扩展：

```text
duplicate_candidates: list[DuplicateCandidateRead]
duplicate_policy: "created_new"
```

上传任务读取结果可补充：

```text
duplicate_count
has_duplicate_risk
```

### 5.3 前端任务

#### 5.3.1 新增统一上传页

新增页面：

```text
/resumes/upload
```

页面能力：

- 选择归属岗位。
- 支持批量选择简历文件。
- 展示每份文件上传、解析、评分状态。
- 展示每份简历的归属岗位。
- 展示疑似重复提示。
- 提供跳转到归属岗位候选人列表入口。

#### 5.3.2 保留岗位内上传页

保留页面：

```text
/jobs/:jobId/resumes/upload
```

行为：

- 自动使用当前岗位作为归属岗位。
- 不要求 HR 再选择岗位。
- 上传结果同样展示疑似重复提示。

#### 5.3.3 上传队列页增强

增强页面：

```text
/jobs/:jobId/upload-tasks
```

补充展示：

- 原文件名
- 归属岗位
- 重复识别状态
- 疑似重复数量

#### 5.3.4 候选人详情页增强

增强内容：

- 展示疑似重复候选人。
- 展示候选人历史岗位关联。
- 提示“疑似重复，仅供 HR 复核，不自动合并”。

### 5.4 验收标准

- HR 可以从统一上传页选择岗位并上传简历。
- HR 仍可以从岗位详情页直接上传简历。
- 每份简历都有明确归属岗位。
- 上传任务能显示归属岗位。
- 同手机号或同邮箱候选人重复上传时出现疑似重复提示。
- 疑似重复候选人不会被自动合并。
- 旧的岗位上传流程仍可用。
- 岗位候选人边界不被破坏。

### 5.5 状态

已完成第一版。当前已新增统一上传接口 `/api/resumes/upload` 和统一上传页 `/resumes/upload`，上传前必须选择归属岗位；岗位内上传接口仍保留，并复用同一套上传、解析、评分和时间线处理链路。新增 `candidate_duplicate_checks` 记录疑似重复候选人，第一版按手机号完全匹配、邮箱完全匹配、姓名 + 城市匹配生成 `pending_review` 提示，不自动合并候选人。上传结果、上传任务队列和候选人详情页均已展示重复风险。后端 V2 验收测试已补充统一上传和重复识别用例，前端构建已通过。

## 6. Phase 19：岗位标准版本与编辑规则

### 6.1 目标

让岗位 JD 和筛选标准变更可追溯，并为后续批量重评打基础。

### 6.2 建议规则

- `open`：允许编辑，但提示可能影响后续评分一致性。
- `paused`：允许编辑，适合作为调整岗位标准后重新开放。
- `closed`：禁止编辑，只允许复制岗位后修改。
- JD、必备条件、加分项、排除条件、评分维度变化时生成标准版本记录。
- 评分结果关联当时使用的岗位标准版本。

### 6.3 后端任务

- 新增岗位标准版本模型。
- 岗位创建时生成初始版本。
- 岗位标准字段变化时生成新版本。
- `closed` 岗位禁止编辑。
- 匹配结果关联岗位标准版本。
- 新增岗位标准版本列表接口。
- 新增标准变化后待重评提示。

### 6.4 前端任务

- 岗位详情展示当前标准版本。
- 岗位详情展示版本历史。
- 关闭岗位隐藏或禁用编辑入口。
- 编辑岗位时展示影响评分一致性的提示。
- 岗位标准变化后展示“建议重新评分”。

### 6.5 验收标准

- 关闭岗位不能编辑。
- 开放和暂停岗位可以编辑。
- 岗位标准关键字段变化会生成版本记录。
- 匹配结果可追溯使用的岗位标准版本。
- 标准变化后有重新评分提示。

### 6.6 状态

已完成第一版。当前已新增 `job_standard_versions` 标准版本表，岗位创建和复制时生成初始版本；岗位 JD、职责、必备条件、加分项、排除条件或评分维度变化时生成新版本。`closed` 岗位禁止编辑和重新开放，只允许复制岗位后修改。匹配结果新增 `job_standard_version_id`，新评分会关联当时使用的岗位标准版本。岗位详情页已展示当前标准版本、版本历史和标准变更后的重新评分提示。后端 V2 验收测试已覆盖版本创建、标准变更、匹配版本追溯和关闭岗位编辑限制，前端构建已通过。

## 7. Phase 20：推荐报告导出

### 7.1 目标

将候选人详情中的匹配结论转化为可沟通材料。

### 7.2 后端任务

- 生成候选人推荐摘要。
- 支持 Markdown 格式导出。
- 后续可扩展 PDF / Word。

### 7.3 前端任务

- 候选人详情页新增“生成推荐摘要”。
- 导出前允许 HR 编辑。
- 支持复制 Markdown 或下载 `.md` 文件。

### 7.4 验收标准

- HR 可以生成单个候选人的推荐摘要。
- 摘要包含匹配分、推荐理由、亮点、短板、风险和面试问题。
- 导出内容不包含敏感筛选判断。
- 导出前可以人工调整。

### 7.5 状态

已完成第一版。当前已新增推荐摘要接口 `/api/jobs/{job_id}/candidates/{candidate_id}/match/recommendation-report`，基于岗位、候选人、最新匹配结果和分项解释生成 Markdown 草稿。候选人详情页已新增推荐摘要面板，支持生成 Markdown、导出前人工编辑、复制 Markdown 和下载 `.md` 文件。第一版不导出 PDF / Word，不保存报告历史。后端 V2 验收测试已覆盖报告生成和联系方式不进入导出内容，前端构建已通过。

## 8. 推荐实施顺序

建议顺序：

```text
Phase 18：统一上传入口与重复候选人识别
  -> Phase 19：岗位标准版本与编辑规则
  -> Phase 20：推荐报告导出
```

原因：

- Phase 18 先解决数据入口和候选人沉淀质量。
- Phase 19 再解决岗位标准变更后的评分追溯。
- Phase 20 最后把已有解释结果转为外部沟通材料。

## 9. V2.1 不做事项

- 自动合并重复候选人。
- 多岗位同时上传同一份简历。
- 完整候选人主档案合并。
- 多角色权限。
- ATS 对接。
- 邮件、短信、企业微信、飞书通知。
- PDF / Word 报告导出。
- 完整 CRM 式人才运营。

## 10. 风险与取舍

### 10.1 重复识别误判

同名同城可能误判，因此第一版只提示，不自动合并。

### 10.2 数据模型扩展风险

第一版尽量复用 `ResumeFile.job_id` 作为归属岗位，避免过早引入多对多岗位归属。

### 10.3 上传入口重复

统一上传和岗位内上传会并存。需要抽取后端上传处理服务，避免逻辑分叉。

### 10.4 历史数据兼容

历史候选人没有重复检查记录，不补历史扫描；只对新上传执行重复识别。

## 11. 后续增强候选

- 人工确认重复候选人。
- 候选人主档案合并。
- 多岗位同时归属同一份简历。
- ZIP 批量上传。
- 文本粘贴录入。
- PDF / Word 推荐报告导出。
- 岗位标准变更后批量重新评分。
