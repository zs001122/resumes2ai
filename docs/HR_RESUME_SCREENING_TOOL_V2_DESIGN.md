# AI 简历筛选工作台 V2 设计方案

> 当前状态说明：V2 / V2.1 / V2.1.1 / V2.1.2 的完成状态、未完成事项和后续路线图见 [V2_STATUS_AND_ROADMAP.md](./V2_STATUS_AND_ROADMAP.md)。本文档保留为产品设计和模块边界说明。

## 1. 文档定位

本文档用于定义 AI 简历筛选工作台第二版本的产品范围、功能设计、优先级和验收标准。

上位文档：

- [HR_RESUME_SCREENING_TOOL_DESIGN.md](./HR_RESUME_SCREENING_TOOL_DESIGN.md)
- [HR_RESUME_SCREENING_TOOL_MVP_DESIGN.md](./HR_RESUME_SCREENING_TOOL_MVP_DESIGN.md)
- [MVP_TASK_BREAKDOWN.md](./MVP_TASK_BREAKDOWN.md)
- [TECH_STACK_DECISION.md](./TECH_STACK_DECISION.md)

V2 必须继续遵循整体设计方案中的产品定位和设计原则：

- AI 辅助 HR 提高初筛效率，不替代 HR 做最终录用决策。
- 所有评分和推荐都必须有解释依据。
- 产品体验保持 B 端工作台风格，强调效率、清晰和可复核。
- 不使用性别、婚育、民族、年龄等敏感信息作为自动筛选依据。
- 支持人工修正 AI 解析结果。
- 每一次关键操作都应可追溯。

如 V2 实现过程中需要改变整体流程、模块边界、数据模型核心含义或合规边界，必须先确认是否同步修改整体设计方案。

## 2. V2 产品目标

MVP 已完成第一版核心闭环：

```text
创建岗位
  -> AI 解析 JD
  -> 确认岗位筛选标准
  -> 上传简历
  -> 解析简历
  -> 原简历对照修正
  -> AI 匹配评分
  -> 候选人列表筛选排序
  -> 候选人详情复核
  -> 状态流转
```

V2 的目标是从“可演示的岗位级初筛闭环”升级为“可试用的招聘工作台”。

V2 重点解决三个问题：

1. HR 每天打开系统时，能快速知道哪些岗位、候选人和异常最需要处理。
2. AI 给出的解析、匹配和风险提示有足够解释依据，HR 能高效复核。
3. 候选人数据开始跨岗位沉淀，为后续人才库和历史人才复用打基础。

## 3. V2 范围边界

### 3.1 V2 必做模块

- 工作台首页
- 批量上传与处理队列增强
- 候选人列表增强
- AI 匹配解释增强
- 原简历字段定位与关键词高亮
- 轻量人才库雏形
- 岗位管理增强
- 候选人备注与操作时间线

### 3.2 V2 可选增强

- 推荐报告导出
- ZIP 批量包上传
- 文本粘贴录入简历
- 重复候选人识别
- 岗位筛选标准版本记录
- 修改岗位标准后批量重新评分

### 3.3 V2 暂不做

- 复杂多角色权限体系
- 完整多人协作审批流程
- 面试日程管理
- 邮件、短信、企业微信、飞书通知
- ATS 系统对接
- 招聘数据大屏
- Offer 管理
- 完整 CRM 式人才库运营
- 图片简历 OCR
- 发布后或关闭后岗位编辑限制

说明：图片简历 OCR、外部通知和 ATS 对接都属于后续增强能力。V2 可以在数据模型和服务边界上预留扩展空间，但不作为当前验收范围。

说明：当前 V2 已支持岗位 `open`、`paused`、`closed` 状态流转，但 V2 第一批暂不限制不同状态下的岗位编辑。该规则已由 V2.1 / V2.1.1 承接：`open` 可编辑但提示影响评分一致性，`paused` 可编辑后重开，`closed` 禁止编辑并通过复制岗位创建新版本。

## 4. V2 核心流程

V2 不改变 MVP 的岗位驱动主流程，而是在主流程前后增加工作台、异常处理、批量操作和人才沉淀能力。

```text
进入工作台首页
  -> 查看待处理岗位、候选人和异常
  -> 进入岗位详情或候选人处理队列
  -> 批量上传简历
  -> 查看上传与解析队列
  -> 处理解析失败或低置信度候选人
  -> 查看候选人列表
  -> 使用组合筛选、批量操作和高匹配队列
  -> 进入候选人详情
  -> 查看 AI 分项解释、原文证据和风险提示
  -> 复核字段、备注、重新评分或修改状态
  -> 将候选人推进沟通、淘汰或入库
  -> 在人才库中沉淀可复用候选人
```

## 5. 功能模块设计

### 5.1 工作台首页

#### 页面目标

让 HR 快速知道今天应该优先处理什么。

首页不做复杂大屏效果，不追求炫技图表，而是提供待办、异常、进展和快捷入口。

#### 核心内容

- 开放岗位数量
- 待筛选候选人数量
- 高匹配候选人数量
- 待沟通候选人数量
- 解析失败候选人数量
- 评分失败候选人数量
- 待复核重复风险数量
- 今日新增候选人数量
- 最近上传记录
- 最近状态变更
- 岗位处理进度摘要

#### 快捷入口

- 创建岗位
- 上传简历
- 查看高匹配候选人
- 查看解析失败
- 查看评分失败
- 复核重复候选人风险
- 查看待沟通候选人

#### 验收标准

- HR 可以在首页看到全局待处理事项。
- HR 可以从首页直接进入关键处理页面。
- 首页展示的统计数据与岗位、候选人、匹配结果状态一致。
- 首页空状态应清晰提示下一步操作。

### 5.2 批量上传与处理队列增强

#### 页面目标

提升批量上传真实可用性，避免单个失败影响整批处理。

#### 核心功能

- 多文件上传队列
- 单个文件独立状态
- 上传进度展示
- 解析进度展示
- 自动评分状态展示
- 失败原因展示
- 单个文件重试
- 批量重试失败项
- 上传结果汇总
- 处理完成后进入候选人列表

#### 状态设计

```text
等待上传
上传中
上传成功
上传失败
等待解析
解析中
解析成功
解析失败
等待评分
评分中
评分成功
评分失败
需要人工确认
疑似重复
```

#### 可选增强

- ZIP 批量包上传
- 文本粘贴录入简历
- 重复候选人检测

#### 验收标准

- 批量上传时，每份简历有独立处理状态。
- 单份简历失败不会阻塞其他简历。
- 解析失败和评分失败有清晰原因。
- HR 可以对失败项执行重试。
- 成功处理后的候选人可以进入对应岗位候选人列表。
- 疑似重复简历处理完成后，上传队列可展示待复核、已忽略和确认重复统计。

### 5.3 候选人列表增强

#### 页面目标

让 HR 在候选人列表页完成大部分初筛动作，减少不必要的详情页跳转。

#### 列表字段

- 姓名
- 当前公司
- 当前岗位
- 工作年限
- 城市
- 最高学历
- 核心技能
- 匹配分
- 推荐等级
- 分项匹配摘要
- 风险标签
- 当前状态
- 是否入库
- 最近更新时间
- 上传时间

#### 筛选条件

- 推荐等级
- 匹配分区间
- 当前状态
- 城市
- 工作年限
- 最高学历
- 技能关键词
- 是否存在风险点
- 是否低置信度
- 是否入库
- 上传时间

#### 排序方式

- 匹配分从高到低
- 上传时间从新到旧
- 最近更新时间从新到旧
- 工作年限从高到低

#### 批量操作

- 批量标记待沟通
- 批量收藏
- 批量淘汰
- 批量加入人才库
- 批量重新评分

#### 可选增强

- 保存筛选视图
- 表格列显示和隐藏
- 候选人对比

#### 验收标准

- HR 可以通过组合筛选快速定位候选人。
- HR 可以对多个候选人执行批量状态操作。
- 列表中可以看到足够的 AI 匹配摘要和风险提示。
- 筛选、排序和批量操作不会破坏岗位维度边界。
- 岗位上下文下的候选人状态、评分、备注和时间线操作不能跨岗位误操作。

### 5.4 AI 匹配解释增强

#### 页面目标

让 AI 匹配结果从“给一个分数”升级为“给出可复核的判断依据”。

#### 分项评分

建议将总匹配分拆解为以下维度：

- 必备条件匹配
- 核心技能匹配
- 项目经验匹配
- 行业经验匹配
- 工作年限匹配
- 学历匹配
- 加分项匹配
- 风险扣分

#### 解释内容

每个候选人的匹配结果应包含：

- 总匹配分
- 推荐等级
- 一句话总结
- 分项评分
- 匹配点
- 不匹配点
- 风险点
- 建议面试问题
- 需要 HR 复核的字段或风险
- 评分生成时间
- 使用的岗位标准版本

#### 原文证据

每个关键匹配点尽量关联简历原文片段：

```json
{
  "dimension": "核心技能匹配",
  "conclusion": "候选人具备 Spring Boot 和 Redis 项目经验",
  "evidence_text": "负责 Spring Boot 微服务开发，使用 Redis 做缓存和分布式锁",
  "confidence": 0.86
}
```

#### 合规约束

- 不得基于性别、婚育、民族、年龄等敏感信息自动推荐或淘汰。
- 风险点应以“待确认”或“建议复核”呈现，不直接等同淘汰原因。
- AI 输出必须经过结构化校验后入库。
- AI 调用失败时必须保存错误原因，并提供重试入口。

#### 验收标准

- 候选人详情页可以看到分项评分。
- 每个匹配结果有明确解释。
- 关键匹配点可以展示原文证据或证据说明。
- 敏感信息不会作为自动评分依据。
- HR 可以重新评分，并看到最新评分结果。

### 5.5 原简历字段定位与关键词高亮

#### 页面目标

提升 HR 对解析结果和 AI 判断的复核效率。

#### 核心功能

- 点击结构化字段后定位到原文片段
- 高亮字段来源片段
- 高亮技能关键词
- 高亮匹配点证据
- 高亮风险点证据
- 字段无明确来源时显示“未定位到原文”

#### 优先字段

V2 优先支持以下字段定位：

- 姓名
- 手机号
- 邮箱
- 当前公司
- 当前岗位
- 工作年限
- 最高学历
- 技能关键词
- 项目经历

#### 验收标准

- HR 点击字段时，原文区域可以定位或展示对应片段。
- 技能和匹配点在原文中有高亮提示。
- 无法定位的字段不会报错，应给出清晰提示。
- 字段定位不影响人工修正能力。

### 5.6 轻量人才库雏形

#### 页面目标

开始沉淀历史候选人，为后续跨岗位复用打基础。

V2 不实现完整 CRM 式人才库，只实现轻量人才列表和跨岗位搜索。

#### 核心功能

- 人才库候选人列表
- 跨岗位搜索候选人
- 按技能、城市、学历、年限筛选
- 查看候选人历史投递岗位
- 查看候选人最近一次匹配结果
- 候选人标签
- 从候选人详情加入或移出人才库

#### 候选人标签

标签可以先采用简单文本标签：

- Java
- 后端
- 高并发
- 电商
- 管理经验
- 待长期关注
- 薪资偏高
- 暂不合适

#### 可选增强

- 新岗位创建后，从人才库推荐历史候选人。
- 疑似重复候选人合并提示。

#### 验收标准

- HR 可以查看所有已入库候选人。
- HR 可以跨岗位搜索候选人。
- HR 可以看到候选人的历史岗位关联。
- 人才库不改变候选人在具体岗位下的状态记录。
- 指定岗位入库时，候选人必须真实关联到该岗位。

### 5.7 岗位管理增强

#### 页面目标

让岗位更像真实招聘项目，而不是单纯的数据容器。

#### 核心功能

- 复制岗位
- 暂停岗位
- 重新开放岗位
- 关闭岗位
- 岗位候选人漏斗统计
- 岗位处理进度
- JD 质量检查

#### 岗位漏斗

建议统计：

- 已上传
- 待筛选
- 已收藏
- 待沟通
- 已淘汰
- 已入库
- 高匹配
- 待人工确认

#### 可选增强

- 岗位筛选标准版本记录
- 修改岗位标准后批量重新评分
- 发布后或关闭后岗位编辑限制

#### 验收标准

- HR 可以复制已有岗位创建新岗位。
- HR 可以暂停、重新开放和关闭岗位。
- 岗位详情页能看到候选人处理进度。
- JD 质量检查能提示岗位描述过短、要求不清晰或评分维度不足。

#### 后续待定规则

当前 V2 第一批不限制 `open`、`paused`、`closed` 状态下的岗位编辑。该规则已由 V2.1 / V2.1.1 承接：

- `open`：允许编辑 JD 和基础信息，但提示可能影响后续评分一致性。
- `paused`：允许编辑，适合作为调整岗位后重新开放的状态。
- `closed`：禁止编辑，只允许复制为新岗位后再修改。
- JD 或评分维度变更后记录岗位标准版本，并提供批量重新评分入口。

### 5.8 候选人备注与操作时间线

#### 页面目标

让关键人工判断和状态变化可追溯。

#### 核心功能

- 候选人备注
- 状态变更记录
- 字段修正记录
- 重新评分记录
- 加入人才库记录
- 批量操作记录

#### 时间线内容

```text
2026-05-09 10:30 上传简历
2026-05-09 10:31 解析成功
2026-05-09 10:32 AI 评分完成，推荐等级 A
2026-05-09 10:40 HR 修改当前公司字段
2026-05-09 10:42 HR 重新评分
2026-05-09 10:45 HR 标记为待沟通
```

#### 验收标准

- 候选人详情页可以查看操作时间线。
- HR 可以新增备注。
- 状态变更、字段修正、重新评分等关键动作会自动记录。
- 时间线记录不允许覆盖原始简历文件。

### 5.8.1 重复候选人人工复核

#### 页面目标

让重复识别从“风险提示”变成可收口的人工作业：HR 可以确认风险是否成立，但系统不自动合并候选人。

#### 核心功能

- 候选人详情展示疑似重复对象、匹配原因和置信度。
- 重复检查支持 `pending_review`、`ignored`、`confirmed_duplicate` 状态流转。
- 工作台展示待复核重复风险，并可直达候选人详情。
- 上传队列展示重复风险的待复核、已忽略和确认重复统计。
- 复核动作写入候选人时间线。

#### 边界约束

- 不自动合并候选人。
- 不修改候选人主档案。
- 不引入多岗位归属模型。
- 确认重复只代表 HR 判断结果，后续主档案合并归入 V4 人才库增强。

### 5.9 推荐报告导出

#### 页面目标

帮助 HR 或猎头将系统判断转化为可沟通材料。

该模块作为 V2 可选增强，不作为第一批硬性验收范围。

#### 核心功能

- 单个候选人推荐摘要
- 批量候选人推荐清单
- 导出 Markdown
- 导出 PDF 或 Word
- 导出前人工编辑

#### 报告内容

- 候选人基础信息
- 匹配分和推荐等级
- 推荐理由
- 主要亮点
- 主要短板
- 风险点
- 建议面试问题

#### 验收标准

- HR 可以基于候选人详情生成推荐摘要。
- 导出内容不包含不应参与筛选的敏感判断。
- 导出前可以人工编辑。

### 6.2 数据设计约束

- 候选人基础信息和岗位下状态应保持分离。
- 人才库状态不应覆盖候选人在具体岗位下的状态。
- 匹配结果必须关联具体岗位和候选人。
- 岗位上下文下的候选人操作必须校验候选人与岗位的真实关联。
- 匹配结果应尽量关联岗位标准版本。
- 操作记录应追加写入，不应覆盖历史。
- JSON 字段应保持 PostgreSQL 迁移兼容。

## 7. API 设计建议

以下为建议 API 方向，具体路径可结合现有后端路由命名调整。

### 7.1 工作台

```text
GET /api/dashboard/summary
GET /api/dashboard/recent-activities
GET /api/dashboard/todos
```

### 7.2 上传队列

```text
GET /api/jobs/{job_id}/upload-tasks
POST /api/jobs/{job_id}/upload-tasks/{task_id}/retry
POST /api/jobs/{job_id}/upload-tasks/retry-failed
```

### 7.3 候选人列表增强

```text
GET /api/jobs/{job_id}/candidates
POST /api/jobs/{job_id}/candidates/bulk-status
POST /api/jobs/{job_id}/candidates/bulk-match
POST /api/jobs/{job_id}/candidates/bulk-add-to-talent-pool
```

说明：上述岗位上下文接口必须只处理当前岗位真实关联的候选人；批量接口应跳过不存在或不属于当前岗位的候选人。

### 7.4 匹配解释

```text
GET /api/jobs/{job_id}/candidates/{candidate_id}/match
GET /api/jobs/{job_id}/candidates/{candidate_id}/match/explanations
POST /api/jobs/{job_id}/candidates/{candidate_id}/match
```

说明：匹配结果和分项解释必须限定在当前岗位与候选人的真实关联上。

### 7.5 人才库

```text
GET /api/talent-pool/candidates
POST /api/candidates/{candidate_id}/talent-pool
DELETE /api/candidates/{candidate_id}/talent-pool
GET /api/candidates/{candidate_id}/job-history
```

说明：人才库可跨岗位搜索；指定 `job_id` 入库时，候选人必须真实关联到该岗位。

### 7.6 备注与时间线

```text
GET /api/jobs/{job_id}/candidates/{candidate_id}/notes
POST /api/jobs/{job_id}/candidates/{candidate_id}/notes
GET /api/jobs/{job_id}/candidates/{candidate_id}/timeline
PATCH /api/jobs/{job_id}/candidates/{candidate_id}/duplicate-checks/{check_id}
```

说明：备注、时间线和重复复核必须限定在当前岗位上下文，不能跨岗位写入或读取。

- 风险提示必须使用复核语气，不使用直接否定语气。
- 原文高亮和字段定位应服务复核，不应影响人工编辑。

## 9. 技术实现建议

### 9.1 后端

- 继续使用 FastAPI、SQLAlchemy、Alembic。
- 上传队列可先保持同步处理和状态记录，不必立即引入 Celery。
- 如批量处理耗时明显，再引入 RQ、Celery 或其他任务队列。
- AI 输出继续通过 AI Provider 适配层调用。
- AI 匹配解释应使用结构化 Schema 校验。
- 操作时间线建议由业务服务统一写入，避免散落在 API 层。

### 9.2 前端

- 继续使用 Next.js、TypeScript、Tailwind CSS。
- 候选人列表增强可逐步引入更完整的表格状态管理。
- 筛选条件应反映在 URL 查询参数中，便于刷新和分享。
- 批量操作需要明确 loading、成功、部分失败和失败状态。
- 原文高亮应优先基于抽取文本实现，暂不依赖 PDF 精确坐标。

### 9.3 文件与解析

- V2 第一批优先增强文本抽取后的定位和高亮。
- ZIP 上传如进入 V2，应解压后复用现有单文件上传处理链路。
- 图片 OCR 不进入 V2 第一批。

## 10. V2 开发优先级

### 10.1 第一批：真实试用最小增强

目标：让 HR 可以更顺畅地处理一批候选人。

- 工作台首页
- 上传队列和失败重试
- 候选人列表组合筛选
- 候选人批量状态操作
- AI 分项评分和解释展示
- 候选人详情时间线基础版

### 10.2 第二批：复核效率和数据沉淀

目标：让 AI 判断更可复核，候选人开始沉淀。

- 原文字段定位
- 关键词和匹配点高亮
- 候选人备注
- 轻量人才库
- 候选人标签
- 岗位漏斗统计

### 10.3 第三批：增强输出和复用

目标：让系统输出进入实际招聘沟通链路。

- 推荐报告导出
- ZIP 批量上传
- 文本粘贴录入
- 重复候选人识别
- 岗位复制
- 岗位标准版本记录
- 修改岗位标准后批量重新评分

## 11. V2 验收标准

V2 完成后，应满足以下验收条件：

- HR 可以从工作台首页看到全局待处理事项。
- HR 可以批量上传简历，并清楚看到每份简历处理状态。
- 解析失败和评分失败都可以定位原因并重试。
- HR 可以在候选人列表中通过组合筛选和批量操作完成初筛。
- 候选人详情页可以展示 AI 分项评分、解释和风险提示。
- 关键匹配点或结构化字段可以展示原文证据或来源片段。
- HR 可以查看候选人操作时间线和备注。
- HR 可以将候选人加入轻量人才库，并跨岗位搜索已入库候选人。
- 岗位上下文下的候选人状态、评分、备注和时间线不会跨岗位误操作。
- 所有关键人工操作都有记录。
- 敏感信息不参与自动评分和推荐。
- MVP 主流程不被破坏。

## 12. 风险与取舍

### 12.1 复杂度风险

V2 功能较多，应按批次实现，不应一次性并行开发所有模块。

建议先完成第一批，再根据试用反馈决定第二批顺序。

### 12.2 AI 可信度风险

AI 分项评分和证据定位可能存在不稳定。设计上必须允许：

- HR 人工复核
- 字段人工修正
- 重新评分
- 风险点标记为待确认
- 本地规则兜底

### 12.3 批量处理性能风险

如果批量上传数量较大，同步处理可能造成请求耗时过长。

V2 第一批可先通过状态记录和单文件处理增强体验；如试用中出现明显等待问题，再引入后台任务队列。

### 12.4 人才库边界风险

V2 的人才库只做轻量候选人沉淀，不做完整 CRM。避免过早引入复杂跟进、归属、权限和营销触达能力。

### 12.5 岗位编辑规则风险

当前 V2 第一批暂不限制发布后或关闭后岗位编辑。该风险已由 V2.1 / V2.1.1 承接处理：引入岗位编辑限制、岗位标准版本、JD 变更后的评分一致性提示、历史匹配结果解释追溯和批量重新评分入口。

## 13. 建议结论

V2 建议以“可试用的招聘工作台”为核心，不急于扩展为完整招聘系统。

最优先开发顺序建议为：

```text
工作台首页
  -> 上传队列与失败重试
  -> 候选人列表增强
  -> AI 分项解释
  -> 操作时间线
  -> 原文定位和高亮
  -> 轻量人才库
```

该顺序能最大程度复用 MVP 已有架构，同时优先提升真实使用价值。
