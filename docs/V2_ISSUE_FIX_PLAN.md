# V2 问题修复方案

> 归档说明：本文档保留岗位候选人边界问题的历史修复方案。该问题已修复并纳入 V2 验收；当前完成状态和后续路线图以 [V2_STATUS_AND_ROADMAP.md](./V2_STATUS_AND_ROADMAP.md) 为准。

## 1. 文档目的

本文档用于描述 V2 当前复核发现的问题、修复边界、接口调整方案、测试补强方案和验收标准，供实施前审核。

本次修复不新增新的业务模块，重点收口 V2 已有能力中的岗位边界、批量操作反馈和验收覆盖。

当前状态：岗位候选人边界修复已实现并提交，提交信息为 `Fix V2 job candidate boundaries`。发布后或关闭后岗位编辑限制仍为后续待定规则，暂未实现。

## 2. 背景与问题概述

V2 已完成工作台首页、上传队列、候选人列表增强、AI 分项解释、备注时间线、轻量人才库、岗位管理增强和 Phase 16 收尾验收。

复核发现当前主链路基本可用，但部分候选人操作接口只校验了“岗位存在”和“候选人存在”，没有严格校验“候选人是否属于当前岗位”。这会带来跨岗位误操作风险。

核心问题：

- 候选人状态更新可能作用到不属于当前岗位的候选人。
- 批量状态更新、批量入库、批量重新评分可能混入其他岗位候选人。
- 重新评分接口可能为错误岗位生成候选人匹配结果。
- 备注和时间线接口可能在错误岗位上下文中写入或读取数据。
- 人才库入库接口在传入 `job_id` 时未校验候选人与该岗位的真实关联。
- 当前验收测试覆盖了 V2 正向主链路，但缺少跨岗位负例。

## 3. 修复目标

本次修复目标如下：

- 所有岗位上下文下的候选人操作必须验证候选人与岗位存在真实关联。
- 单个候选人接口遇到跨岗位候选人时应返回明确错误。
- 批量接口遇到不存在或不属于当前岗位的候选人时应跳过，并反馈部分成功。
- 人才库仍保持跨岗位搜索能力，但入库动作必须绑定真实岗位来源。
- 补充自动化测试，覆盖跨岗位误操作负例。
- 不破坏 MVP 和 V2 已有正向主流程。

## 4. 非目标

本次不处理以下事项：

- 不引入多用户、权限、角色体系。
- 不实现完整 ATS 或 CRM 归属模型。
- 不改变候选人、岗位、人才库的现有核心数据模型。
- 不重构上传、解析、评分的整体流程。
- 不引入异步任务队列。
- 不在本次修复中实现发布后或关闭后岗位编辑限制。

## 5. 修复范围

### 5.1 后端 Repository

建议在 `backend/app/repositories/resumes.py` 中新增统一方法：

```python
def get_candidate_for_job(self, job_id: str, candidate_id: str) -> tuple[Candidate, ResumeFile] | None:
    ...
```

或新增更轻量的判断方法：

```python
def candidate_belongs_to_job(self, job_id: str, candidate_id: str) -> bool:
    ...
```

推荐使用 `get_candidate_for_job`，因为多数接口不仅需要判断归属，还会继续使用候选人或简历文件。

判断规则：

```text
存在 ResumeFile 记录：
- ResumeFile.job_id == job_id
- ResumeFile.candidate_id == candidate_id
- ResumeFile.parse_status == "success"
```

说明：

- `parse_status == "success"` 可确保候选人来自已成功解析的岗位简历。
- 如果后续需要允许失败解析候选人参与某些操作，应单独设计接口，不在本次修复范围内。

### 5.2 候选人状态接口

影响接口：

- `PATCH /api/jobs/{job_id}/candidates/{candidate_id}/status`
- `POST /api/jobs/{job_id}/candidates/bulk-status`
- `POST /api/jobs/{job_id}/candidates/bulk-add-to-talent-pool`

修复策略：

- 单个状态更新：
  - 岗位不存在：返回 `404`
  - 候选人不存在或不属于岗位：返回 `404`
  - 状态非法：返回 `400`
- 批量状态更新：
  - 岗位不存在：返回 `404`
  - 候选人不存在或不属于岗位：跳过
  - 合法候选人正常更新状态和写入时间线
- 批量加入人才库：
  - 复用批量状态更新逻辑
  - 只允许当前岗位下候选人被标记为 `archived`

### 5.3 重新评分接口

影响接口：

- `POST /api/jobs/{job_id}/candidates/{candidate_id}/match`
- `POST /api/jobs/{job_id}/candidates/bulk-match`

修复策略：

- 单个重新评分：
  - 必须验证候选人属于当前岗位
  - 不属于时返回 `404`
  - 只为合法岗位候选人生成 `CandidateMatch`
  - 只为合法匹配结果生成分项解释
- 批量重新评分：
  - 跳过不存在或不属于当前岗位的候选人
  - 只对合法候选人生成新评分和时间线

### 5.4 备注和时间线接口

影响接口：

- `GET /api/jobs/{job_id}/candidates/{candidate_id}/notes`
- `POST /api/jobs/{job_id}/candidates/{candidate_id}/notes`
- `GET /api/jobs/{job_id}/candidates/{candidate_id}/timeline`

修复策略：

- 必须验证候选人属于当前岗位。
- 不属于时返回 `404`。
- 创建备注时，`payload.job_id` 不应覆盖 URL 中的 `job_id`。
- 时间线查询只返回当前岗位上下文下的事件。

### 5.5 人才库入库接口

影响接口：

- `POST /api/candidates/{candidate_id}/talent-pool`

当前行为：

- 如果 payload 传入 `job_id`，接口直接使用该岗位写入 `archived` 状态。

修复策略：

- 如果 payload 传入 `job_id`：
  - 必须验证候选人属于该岗位
  - 不属于时返回 `404`
- 如果 payload 未传入 `job_id`：
  - 继续使用候选人最近一次简历关联岗位
  - 如果没有任何岗位关联，返回 `400`

保留行为：

- 人才库列表仍可跨岗位搜索已入库候选人。
- 移出人才库仍可移除候选人所有 `archived` 岗位状态。

## 6. 批量接口返回结构增强

当前批量接口返回成功处理的列表，前端可通过请求数量与返回数量判断部分成功。

建议新增统一批量响应结构：

```python
class CandidateBulkActionResult(BaseModel):
    requested_count: int
    success_count: int
    skipped_count: int
    skipped_candidate_ids: list[str]
    items: list[CandidateStatusRead] | list[CandidateMatchRead]
```

适用接口：

- `POST /api/jobs/{job_id}/candidates/bulk-status`
- `POST /api/jobs/{job_id}/candidates/bulk-add-to-talent-pool`
- `POST /api/jobs/{job_id}/candidates/bulk-match`

兼容性说明：

- 这是响应结构变更，前端需要同步适配。
- 如果希望降低改动风险，可第一阶段保持当前返回列表，仅增强前端提示和测试；第二阶段再切换结构化批量结果。

推荐方案：

- 本次先保持当前返回列表，避免扩大改动面。
- 前端继续使用 `requestedCount` 与 `result.length` 判断部分成功。
- 后续如需要更精确失败原因，再单独升级批量响应结构。

## 7. 前端调整方案

影响页面：

- `frontend/app/jobs/[jobId]/candidates/page.tsx`
- `frontend/lib/api.ts`

修复策略：

- 保留现有批量成功/部分完成提示。
- 当返回数量小于请求数量时，提示：

```text
部分完成：成功处理 X / Y 位候选人，未处理项可能已不存在或不属于当前岗位。
```

- 单个状态更新、重新评分、备注等接口收到 `404` 时沿用现有错误提示机制。
- 不新增复杂弹窗或失败明细列表，保持 Phase 16 修复范围克制。

## 8. 测试补强方案

### 8.1 后端自动化测试

扩展 `backend/tests/test_v2_acceptance.py`，新增跨岗位负例。

测试数据：

- 创建岗位 A
- 创建岗位 B
- 岗位 A 上传候选人 A1
- 岗位 B 上传候选人 B1

测试场景：

- 使用岗位 A 更新 B1 状态，期望 `404`
- 使用岗位 A 为 B1 创建匹配结果，期望 `404`
- 使用岗位 A 为 B1 创建备注，期望 `404`
- 使用岗位 A 查询 B1 时间线，期望 `404`
- 使用岗位 A 批量更新 `[A1, B1]`，期望只处理 A1
- 使用岗位 A 批量重新评分 `[A1, B1]`，期望只处理 A1
- 使用 `POST /api/candidates/{B1}/talent-pool` 并指定岗位 A，期望 `404`
- 使用 `POST /api/candidates/{B1}/talent-pool` 并指定岗位 B，期望成功

## 10. 后续待定规则

### 10.1 发布后岗位编辑限制

当前 V2 版本中，岗位更新接口尚未限制岗位状态。`open`、`paused` 和 `closed` 状态下的岗位仍可通过编辑接口修改。

建议后续单独评审以下规则：

- `open`：允许编辑 JD 和基础信息，但需要提示可能影响后续评分一致性。
- `paused`：允许编辑，适合作为调整岗位后重新开放的状态。
- `closed`：建议禁止编辑，只允许复制为新岗位后再修改。
- 若后续引入岗位标准版本，应在 JD 或评分维度变更后记录标准版本，并提供批量重新评分入口。

该规则暂不进入本次 V2 边界修复实现。

13. 提交修复。

## 12. 验收标准

本修复完成后必须满足：

- 不属于当前岗位的候选人不能被单个状态更新。
- 不属于当前岗位的候选人不能被单个重新评分。
- 不属于当前岗位的候选人不能被写入当前岗位备注。
- 不属于当前岗位的候选人不能读取当前岗位时间线。
- 批量操作会跳过不存在或不属于当前岗位的候选人。
- 人才库指定 `job_id` 入库时必须校验真实岗位来源。
- V2 正向端到端验收仍然通过。
- MVP 创建岗位、上传简历、解析、评分、状态流转仍然可用。

## 13. 风险与回滚

### 风险

- 批量接口如果改动响应结构，会影响前端调用。
- 归属校验如果过严，可能影响历史数据中缺少 `ResumeFile` 关联的候选人。
- 测试数据和真实数据在 `parse_status` 上可能存在差异。

### 降低风险措施

- 本次不改变批量接口响应结构，只增强校验逻辑。
- 使用 `ResumeFile` 作为岗位候选人归属来源，符合当前 V2 岗位驱动设计。
- 对历史缺少关联的数据，先保持不可在岗位上下文操作，可通过人才库列表查看。

### 回滚方式

如修复后出现阻断性问题，可回滚本次提交；由于不涉及数据库迁移，回滚成本较低。
